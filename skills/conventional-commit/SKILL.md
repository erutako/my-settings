# 適切な粒度でのGit Commit ワークフロー

あなたはGit操作とConventional Commitsに精通したエージェントです。ユーザーからコミットの指示があった場合、**利用可能なターミナルツールを使用して、以下の手順を実際に実行してください。**

## 実行プロセス

`git diff`で差分がなくなるまで、以下の1→2→3→4のサイクルを繰り返します。

---

### Step 1: 差分の把握

**Working Tree と Staging Area の差分を確認する**

```bash
# 未ステージングの変更（Working Tree vs Index）
git diff

# ステージング済みの変更（Index vs HEAD）
git diff --cached
```

**解釈のポイント:**
- `git diff`: ファイルを編集したが`git add`していない変更
- `git diff --cached`: `git add`済みで、まだコミットしていない変更
- 両方実行して、変更の全体像を把握する

---

### Step 2: 適切な粒度でステージング

**原則: 1 task = 1 commit**

Conventional Commitsの粒度に従い、1つのコミットには1つの論理的なタスクの変更のみを含める。

#### 2-1. 単一ファイルが単一タスクの場合

```bash
git add src/components/Header.tsx
```

#### 2-2. 複数ファイルが同じタスクに属する場合

```bash
git add src/components/Header.tsx src/styles/header.css
```

#### 2-3. 1ファイル内に複数タスクが混在する場合 → `git add -p` を使用

```bash
git add -p src/components/ContactForm.tsx
```

**`git add -p`の操作:**
- `y` (yes): このhunkをステージングに追加
- `n` (no): このhunkをスキップ
- `s` (split): hunkをより小さな単位に分割
- `e` (edit): 手動でhunkを編集
- `q` (quit): 終了
- `?`: ヘルプ表示

**例:** `src/components/ContactForm.tsx` に「お問い合わせフォームの送信処理の追加」と「デバッグ用の `console.log` の削除」が混在している場合、`git add -p`で前者のみをステージングし、1コミット目を作成。残りは次のコミットに。

---

### Step 3: コミットメッセージを作成してコミット

**重要: コミットメッセージは必ず日本語で記述する。**

**フォーマット:**

```
<type>: <日本語で簡潔な説明>

（空行）

変更理由を日本語で記載する。
```

**実行例:**

```bash
git commit -m "docs: サービス紹介と料金の原稿を追加

ランディングページの構成に合わせ、機能説明と料金表のセクションを記載した。"
```

---

### Step 4: コミット完了後の説明

各コミット実行後、ユーザーに対して以下を簡潔に出力する。

1. **コミットメッセージの表示**（実際に実行した `git commit` のメッセージ全文）
2. **説明（簡潔に）:**
   - **コミット単位の理由:** なぜその変更を1つのコミットにまとめたか（例: 同じタスクに属するため、論理的に独立した変更のため）
   - **メッセージの理由:** その type と説明文を選んだ根拠（例: 新機能追加のため `feat`、変更理由を本文で補足）

**出力例:**

```
---
コミットメッセージ:
docs: サービス紹介と料金の原稿を追加

ランディングページの構成に合わせ、機能説明と料金表のセクションを記載した。

---
説明:
- **コミット単位:** `docs/service.md` と `docs/pricing.md` は同一ページ向けの原稿作成という単一タスクで密接に関連しており、片方だけrevertすると掲載内容が矛盾するため1コミットにまとめました。
- **メッセージ:** サイト用ドキュメントの追加のため `docs` を選択。本文で掲載の意図（LPの構成に沿った説明と料金の明示）を補足しました。
---
```

---

## Conventional Commits 型一覧（日本語説明用）

| 型 | 用途 |
|---|---|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更（フォーマット、空白等） |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `build` | ビルドシステム・依存関係の変更 |
| `ci` | CI設定の変更 |
| `chore` | その他の変更（リポジトリメンテナンス等） |

## 具体例

### 例1: シンプルな単一タスク

**状況:** お問い合わせフォームからAPIへ送信する処理を追加した

```bash
git diff
# → src/components/ContactForm.tsx, src/api/contact.ts が変更

git add src/components/ContactForm.tsx src/api/contact.ts
git commit -m "feat: お問い合わせフォームの送信処理を追加

入力内容をバックエンドの問い合わせAPIへPOSTする処理を実装した。"
```

### 例2: 1ファイルに複数タスクが混在

**状況:** `ProductList.tsx` に「並び替えUIの追加」と「リスト描画のリファクタリング」が混在

```bash
git add -p src/components/ProductList.tsx
# 並び替えに関連するhunkには y、リファクタリングには n

git commit -m "feat: 商品一覧の並び替えを追加

価格順・新着順で並べ替えられるセレクトを実装した。"

# 再度差分確認
git add -p src/components/ProductList.tsx
# リファクタリングのhunkに y

git commit -m "refactor: 商品カードの描画処理を共通化

重複していた画像とタイトルの表示処理を小さなコンポーネントに切り出した。"
```

### 例3: バグ修正とスタイル修正の分離

```bash
# 1つ目: バグ修正
git add -p src/utils/cart.ts
git commit -m "fix: 送料無料ライン判定の計算ミスを修正

税込み合計と税抜き合計を取り違えていたため、閾値との比較がずれるケースを修正した。"

# 2つ目: スタイル修正
git add src/utils/cart.ts
git commit -m "style: Prettier に従いインデントを修正"
```

### 例4: テストの追加

```bash
git add src/components/ContactForm.test.tsx
git commit -m "test: お問い合わせフォームの単体テストを追加

送信ボタン押下時のバリデーションとAPI呼び出しをモックして検証した。"
```

## Git Commit のベストプラクティス

### 1. Atomic Commits（原子的なコミット）

- **1コミット = 1つの論理的な変更**
- 変更を後からrevertする際に、必要な部分だけ選んでrevertしやすくなる
- `git bisect` でバグ導入コミットを特定しやすくなる

### 2. コミットメッセージの品質

- **言語:** タイトル・本文ともに**必ず日本語**で記述する
- **1行目（タイトル）:** 50文字以内で、変更内容を要約。命令形で書く（「追加する」而非「追加した」も可、簡潔さを優先）
- **本文:** 何を（what）ではなく、なぜ（why）を説明
- **空行:** タイトルと本文の間に必ず空行を入れる

### 3. 分離すべき変更

- 機能追加とバグ修正
- 実装とリファクタリング
- 機能変更とスタイル・フォーマット変更
- プロダクションコードとテストコード（別コミットでも、同じコミットに含めても可。テストが機能に密接に関連する場合は同一コミットもあり）

### 4. コミット前の確認

- `git diff --cached` でステージング内容を最終確認
- デバッグ用の `puts` / `console.log` / `print` が残っていないか確認
- 不要なファイルが誤って含まれていないか確認

### 5. 粒度の判断基準

- **分割する:** 変更を説明するのに「と」「および」で繋ぐ場合（例：「Aを追加し、かつBを修正した」→2コミット）
- **まとめる:** 変更が密接に関連し、片方だけrevertすると不整合が起きる場合

---

## 実行時の注意事項

1. **自律的に実行する:** ユーザーに確認を求めることも可能だが、手順に従ってターミナルで実際にコマンドを実行することを優先する
2. **1サイクルずつ進める:** 複数コミットをまとめて行わず、1コミット完了→Step 4で説明出力→`git diff`確認→次のコミット、の順で進める
3. **差分がなくなるまで繰り返す:** `git diff` と `git diff --cached` の両方が空になるまで、Step 1→2→3→4 を繰り返す
4. **エラー時:** コンフリクトや想定外の状態の場合は、状況を説明し次のアクションを提案する
5. **Pull Request コメント対応時:** コメント対応であることを理由にコミットをまとめない。本ルールの「1 task = 1 commit」「分離すべき変更」等に従い、あくまで適切な粒度でコミットを分割する
