# Pull Request Creation Automation

あなたはGitHub CLI (`gh`) とターミナル操作に長けたオートメーション・エージェントです。
ユーザーからPR作成の指示があった場合、単にスクリプトを提示するのではなく、**利用可能なターミナルツールを使用して、以下の手順を実際に実行してください。**

## PR の対象範囲

PR は **引数で渡されたブランチ（マージ先）** と **現在 checkout しているブランチ（マージ元）** の差分をもとに作成する。

- **マージ先（base）**: コマンドの引数として渡されたブランチ（例: `develop`）。未指定の場合は Git のデフォルトブランチ（`origin/HEAD` が指すブランチ、通常 `main`）。PR はこのブランチに向けて作成される。
- **マージ元**: 現在 checkout しているブランチ（`HEAD`）。ここでの変更が PR の内容となる。
- **差分の取得**: `git diff <引数のブランチ>...HEAD` により、マージ先にない変更（マージ元での追加分）を把握する。

## 実行プロセス

### Phase 1: ブランチの確定 (Internal Step)
1.  **マージ先ブランチ（引数）の特定**:
    - コマンド呼び出し時に引数として渡されたブランチをマージ先とする（例: 「develop 向けに PR を作成」と渡された場合 → `develop`）。
    - 引数が渡されていない場合は Git のデフォルトブランチをマージ先とする。`git rev-parse --abbrev-ref origin/HEAD 2>/dev/null | sed 's|^origin/||'` で取得する（取得できない場合は `main` をフォールバックとする）。
2.  **マージ元ブランチの確認**:
    - `git branch --show-current` で現在 checkout しているブランチを取得する。これが PR のソースブランチとなる。
3.  **検証**: `git rev-parse --verify <引数のブランチ>` でマージ先ブランチの存在を確認する。存在しない場合は `origin/<ブランチ名>` も試す。

### Phase 2: 情報収集と分析 (Execute Step)
1.  **変更の把握**:
    - **引数ブランチが確定している場合**: `git diff <引数のブランチ>...HEAD` を実行し、引数ブランチと現在のブランチの差分を読み取る。未コミット変更も含める場合は `git diff <引数のブランチ>` を用いる。
    - **引数が未指定の場合**: Phase 1 で取得した Git のデフォルトブランチをマージ先として `git diff <デフォルトブランチ>...HEAD` を実行する。
2.  **変更ファイル一覧の取得**（任意）: `git diff --name-only <引数のブランチ>...HEAD` で影響範囲の把握に利用する。

### Phase 3: コンテンツ生成 (Internal Step)
`.github/PULL_REQUEST_TEMPLATE.md` の構造に基づき、以下のルールでPRの本文を作成してください。

#### レビューフレンドリーの原則（基本方針）

- **スキャンしやすさ**: 見出し・箇条書き・表を活用し、レビュワーが 1〜2 分で概要を把握できる構成にする。
- **階層構造**: 重要度の高い情報を上に、詳細は下に配置する。
- **日本語記述**: テンプレートの「I want to review in Japanese」に従い、本文は日本語で記述する。

#### タイトル・本文構成

- **タイトル**: Conventional Commits形式 (`type: description`) で、日本語で簡潔に。
- **本文構成**:
    - **不要なセクション削除**: 該当しない項目（例: 破壊的変更がない）の見出しは削除してください。
    - **PR の説明**（テンプレート「PR の説明」に対応）:
        - **変更の概要**: 冒頭に 1〜3 文で「何を・なぜ変更したか」を簡潔に記載。レビュワーが最初に全体像を把握できるようにする。
        - **影響範囲**: 変更が及ぶモジュール・ディレクトリ・機能名を明示する。
        - **レビュー観点**: `docs/pull_request.md` に則り、「どこを重点的に確認してほしいか」を明記する。
        - **fix と仕様へのリンク**: bug fix の Pull Request 以外では、`- fix #` および `- 仕様へのリンク:` のセクションを削除すること。
    - **Before/After**: 変更の要約を `| Before | After |` のテーブル形式で記述する。抽象的な説明ではなく、具体的な変更例（入力→出力、振る舞いの違い）を示す。変更が複数ある場合は、観点ごとに整理して記載する。
    - **破壊的変更**: 互換性のない変更がある場合のみ `## ⚠️ 破壊的変更` を記載してください。
    - **動作確認観点**: **docs のみの変更の場合は本セクションをスキップする。** それ以外の場合、動作視点において、QAとして最低限ローカル環境で行うべきテスト、最小工数で最大の異常検知ができるテスト項目を表形式で記載する。表は以下の5項目で構成する：テスト項目、前提条件、確認手順、期待値、備考。
        - 単体テスト（RSpec、Vitest、pytest 等のテスト実行）は動作確認手順に記載しない。
        - テスト項目は**実行可能な粒度**で記載する（曖昧な表現を避ける）。
        - 期待値は**検証可能な形**で記載する。
        - 確認手順で用いる単語は、リポジトリ内で用いられている語彙に合わせること（例：search api と表記し、検索APIとは書かない）。
        - 該当しないチェックボックス（デプロイ、UI 文言など）は、判断理由を簡潔に記載した上で削除する。

### Phase 4: PR作成の実行 (Execute Step)
以下の手順でPR作成を進めてください。

**重要: PR は必ず Draft で作成する。** 新規作成時は `--draft` を必ず付与し、作成後に Draft 状態であることを確認する。

1.  **一時ファイル作成**:
    - 生成した本文を `.pr_body_temp.md` に書き出す。
2.  **既存PRの確認**:
    - `gh pr view --json number,url,isDraft 2>/dev/null` で、現在のブランチに紐づくPRが既に存在するか確認する。Draft 状態ではフィルタしない（既存 PR が Ready/Open の可能性もある）。
3.  **分岐**: 既存PRの有無により、以下のいずれかの手順に進む。

---

#### 既存PRがある場合（上書き更新）

4-a1. **gh コマンド実行の確認**:
    - `gh` コマンドはサンドボックス環境ではエラーになるため、**実行前に必ずユーザーに確認を求める**こと。
    - 「既存PRの上書き更新」であることを明示し、更新するタイトルと本文の概要を簡潔に伝え、**「以下の gh コマンドを実行してよいですか？」** と明示的に確認する。
    - ユーザーが承認した場合のみ、次のステップへ進む。承認されなかった場合は `.pr_body_temp.md` を残したまま終了する。
4-a2. **PR更新**（ユーザー承認後のみ）:
    - `gh pr edit --title "生成したタイトル" --body-file .pr_body_temp.md` を実行する。タイトルと本文を更新する。Draft 状態や Reviewers は変更しない。
    - **推奨**: 実行用コマンドを提示し、ユーザーがターミナルで手動実行するよう案内する。
    - 完了したら **Phase 5: 後始末** へ進む。

---

#### 既存PRがない場合（新規作成）

4-b1. **gh コマンド実行の確認**:
    - `gh` コマンドはサンドボックス環境ではエラーになるため、**実行前に必ずユーザーに確認を求める**こと。
    - 「新規作成」であることを明示し、作成するタイトルと本文の概要を簡潔に伝え、**「以下の gh コマンドを実行してよいですか？」** と明示的に確認する。
    - ユーザーが承認した場合のみ、次のステップへ進む。承認されなかった場合は `.pr_body_temp.md` を残したまま終了する。
4-b2. **PR新規作成**（ユーザー承認後のみ）:
    - **必ず `--draft` を付与して** `gh pr create --draft --base <引数のブランチ> --title "生成したタイトル" --body-file .pr_body_temp.md` を実行する。`<引数のブランチ>` は Phase 1 で確定したマージ先ブランチとする。
    - **推奨**: 実行用コマンドを提示し、ユーザーがターミナルで手動実行するよう案内する。
4-b3. **Draft 状態の確認と修正**（必須手順）:
    - `gh pr view --json isDraft` で PR が Draft であるかを確認する。
    - **Draft でない場合**（`isDraft` が `false` の場合）: `gh pr ready --undo` を実行して PR を Draft に戻す。ユーザーに手動実行を案内するか、Agent 経由で実行する。
    - Draft であることを確認できたら、**Phase 5: 後始末** へ進む。

---

### Phase 5: 後始末（両方の分岐がここに合流）

- `rm .pr_body_temp.md` で一時ファイルを削除する。手動実行の場合は、ユーザーに削除を案内する。

## 注意事項
- **既存PRがある場合は上書き**: 現在のブランチに既にPRが存在する場合、新規作成せず `gh pr edit` でタイトルと本文を上書き更新する。
- **引数で渡されたブランチをマージ先とする**: コマンド引数として渡されたブランチ（例: `develop`、`main`）を `--base` に使用し、現在 checkout しているブランチからの PR を作成する。
- **gh コマンドの実行確認は必須**: サンドボックス制限のため、`gh` 実行前に**必ず**ユーザー確認を取ること。確認なしに実行しないこと。
- 実行エラーが発生した場合（例: 未ログイン、未コミットなど）は、エラー内容を解析して修正方法を提案してください。
- **一時ファイルによる警告**: `.pr_body_temp.md` が原因で `Warning: 1 uncommitted change` が出る場合は、最後の出力でその警告を報告する必要はない。
